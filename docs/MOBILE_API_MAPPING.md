# Mobile API Mapping — Pregnancy Care (Android, React Native)

Written 2026-10-19, before any integration code. Every row below was checked against the
backend source in `apps/api/src`, not only against the Swagger document. Where the two
disagreed, the source wins; no disagreements were found.

**What this document is for:** it is the contract the mobile app is allowed to rely on. If an
endpoint, field or behaviour is not listed here, the app must not assume it exists.

## 2. Transport

| Item | Value |
|---|---|
| Framework | NestJS 12, URI versioning, default version `1` |
| Prefix | every route is `/v1/...` (no separate global prefix) |
| Local port | `4000` (`PORT`, `apps/api/.env.example`) |
| Local database | Postgres 17 in Docker on host port **5434** (`infra/docker/docker-compose.yml`) |
| Content type | `application/json`; `PUT`/`PATCH`/`POST` bodies rejected by a strict global `ValidationPipe` |
| CORS | `CORS_ORIGINS` allowlist, `credentials: true`, exposes `x-request-id` and `set-auth-token`. **Not relevant to the native app** — React Native is not a browser origin |
| Request id | `requestIdMiddleware` sets `x-request-id` on every response and echoes a client-supplied one. The app will send its own id and surface it in error screens for support |
| Swagger UI | `GET /docs` and `GET /docs/openapi.json`, **non-production only** |

### Base URL per target

`EXPO_PUBLIC_API_URL` already exists in `apps/mobile/.env.example`; `src/constants/api.ts`
appends `/v1`. The value differs per target:

| Target | `EXPO_PUBLIC_API_URL` | Note |
|---|---|---|
| Android emulator (AVD) | `http://10.0.2.2:4000` | `10.0.2.2` is the emulator's alias for the host loopback. `localhost` would mean the emulator itself |
| Physical Android device (USB) | `http://127.0.0.1:4000` with `adb reverse tcp:4000 tcp:4000` | Preferred: no firewall or LAN exposure, and no cleartext traffic over the network |
| Physical Android device (Wi-Fi) | `http://<dev-machine-LAN-IP>:4000` | Needs the Mac firewall to allow inbound 4000 and a cleartext-permitted debug network config |
| Staging / production | `https://...` | TLS only. TLS verification is never disabled, and cleartext is never enabled for release builds |

## 3. Authentication — guest-first, which this backend supports properly

Three credential schemes reach the same global, default-deny guard:

| Scheme | Header | Who |
|---|---|---|
| Anonymous session | `Authorization: Anonymous <secret>` | Guest use. **This is the app's default path** |
| Bearer token | `Authorization: Bearer <token>` | Registered account (Better Auth `bearer()` plugin) |
| Cookie | `better-auth.session_token` | Web only; the app will not use cookies |

Facts that shape the app:

- `POST /v1/anonymous-sessions` with `{ platform: "android" }` returns `{ id, secret, expiresAt }`.
  **The secret is shown once and cannot be recovered** — it goes straight into Android Keystore-backed
  secure storage, never `AsyncStorage`, never a log.
- Sessions slide: any request within the TTL (`ANONYMOUS_SESSION_TTL_DAYS`, default 180) extends
  `expiresAt`. An expired or linked session stops authenticating, so the app must handle 401 on a
  previously working secret by offering to start fresh or sign in.
- Sign-up and sign-in return the bearer token in the **`set-auth-token` response header**, not in the
  body (`apps/api/test/helpers.ts:59`). The API client must read that header.
- `POST /v1/anonymous-sessions/link` (`{ secret }`, user credentials) migrates guest data into an
  account and returns per-table counts. It returns **409 if the account already holds health data**,
  which the app must explain rather than retry.
- Password is minimum **12 characters** (`PASSWORD_MIN_LENGTH`). Maximum 128.
- **Password reset and email verification are disabled (404)** — no email provider is configured. The
  app must not show a "Forgot password?" flow.
- Better Auth replies use **Better Auth's own error shape**, not the platform `ApiError` envelope. The
  API client needs two error parsers.

### Consent gate — blocks writes until granted

Every health-data write (`pregnancies`, `cycles`, `daily-logs`, task notes) first calls
`assertHealthDataConsent` and returns **403 `CONSENT_REQUIRED`** if
`health_data_processing` was never granted. Onboarding must therefore run:

1. `POST /v1/anonymous-sessions` → store secret
2. `POST /v1/me/consents` `{ purpose: "health_data_processing", granted: true, policyVersion, source }`
3. `PUT /v1/me/profile` (time zone — the server computes "today" from it)
4. `POST /v1/pregnancies`

`source` must match `/^[a-z][a-z_]{1,39}$/` (e.g. `onboarding`). `policyVersion` is a string ≤ 32
chars that the app must pin to the privacy text actually displayed.

## 4. Error envelope

All Nest routes:

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "The request is invalid.",
             "requestId": "…", "details": [ { "path": "dueDate", "message": "…" } ] } }
```

`code` ∈ `VALIDATION_ERROR, UNAUTHORIZED, FORBIDDEN, CONSENT_REQUIRED, PREMIUM_REQUIRED,
NOT_FOUND, CONFLICT, PAYLOAD_TOO_LARGE, RATE_LIMITED, INTERNAL_ERROR`.

| Status / code | What the app does |
|---|---|
| 400 `VALIDATION_ERROR` | Map `details[].path` onto form fields; never show the raw message alone |
| 401 `UNAUTHORIZED` | Credentials gone or expired → clear token, return to welcome, offer sign-in or a new guest session. Never silently retry |
| 403 `CONSENT_REQUIRED` | Open the consent sheet, explain why, retry after granting |
| 403 `PREMIUM_REQUIRED` | Show the locked state. No purchase flow exists (see gaps) |
| 403 `FORBIDDEN` | "This needs a signed-in account" (guest hit a `@UserOnly()` route) |
| 404 `NOT_FOUND` | Empty state, not an error, for `/pregnancies/current` and week guides |
| 409 `CONFLICT` | Explain the specific conflict (active pregnancy exists, overlapping cycle, reminder limit, link conflict) |
| 429 `RATE_LIMITED` | Back off; show "Try again in a moment" |
| 5xx / network / timeout | Offline or server banner + Retry. Writes are **never** auto-retried (see §7) |

Ownership is enforced in every query; another owner's id returns **404, not 403**, so the app must
treat 404 on a known id as "gone", not as a bug.

## 5. Screen → endpoint map

Only verified endpoints appear. "Local only" means on-device storage with a visible
"saved on this device" marker — never presented as synced.

### Onboarding
| Step | Endpoint | Notes |
|---|---|---|
| Get Started (guest) | `POST /v1/anonymous-sessions` `{platform:"android"}` → 201 | Secret → secure storage |
| Create account | `POST /v1/auth/sign-up/email` `{email,password,name?}` → 200 | Token in `set-auth-token` |
| Sign in | `POST /v1/auth/sign-in/email` | 5/min limit |
| Keep guest data after signing in | `POST /v1/anonymous-sessions/link` `{secret}` | 409 if account has health data |
| Consent | `POST /v1/me/consents` | Required before any health write |
| Time zone / locale | `PUT /v1/me/profile` | IANA zone; drives server-side "today" |
| Pregnancy dates | `POST /v1/pregnancies` | See dating methods below |

**Dating** — the client never computes the due date; it sends one method and the API returns the
estimate (`apps/api/src/pregnancy/dating.ts`, unit-tested in `dating.spec.ts`):

| `dating.method` | Required fields | Rules |
|---|---|---|
| `lmp` | `lmpDate` (ISO date), `cycleLengthDays?` | 20–45 days; estimate shifts by `cycleLength − 28` |
| `due_date` | `dueDate` | When the user already has a clinician's date |
| `ultrasound` | `scanDate`, `gestationalWeeks` (4–40), `gestationalDays` (0–6) | |
| `ivf` | `transferDate`, `embryoAgeDays` (2–7) | |

`source: "self" | "clinician"`. **409 if a pregnancy is already active.**

> If the user knows both LMP and a clinician's due date, the app shows both estimates
> side by side and asks which to record — it does not silently pick one. The screen can do
> this honestly because `POST /v1/pregnancies` is one call per method and
> `PUT /v1/pregnancies/current/dating` records a correction with its shift in days.

## 6. Content availability — the largest functional risk

The content *pipeline* is complete (draft → review → publish, with reviewer credentials and a
+12-month review due date). **No week guide and no article has been written or clinically
reviewed yet**, and there is no seed script (`apps/api/prisma/` has migrations only).

Consequence, today, against an empty database:

- `GET /v1/pregnancies/current/week` → `guide: null`
- `GET /v1/week-guides/{week}` → 404 for all 42 weeks
- `GET /v1/articles` → `{ items: [], page: { total: 0 } }`
- `GET /v1/readiness/tasks` → `[]`

So the Baby Development card, My Journey content, the educational library and Today's Plan are
**structurally complete but empty** until content is authored and reviewed. The app will ship
honest empty states ("This week's guide hasn't been published yet"). It will not invent
development facts, size comparisons, reviewer names or review dates — `docs/product/ROADMAP.md`
lists clinical review of health content as an unmet release requirement, and
`PREGNANCY_APP_PRD.md` §20 requires it per feature.

## 7. Write safety

- `PUT` routes (`/me/profile`, `/daily-logs/{date}`, `/readiness/tasks/{id}/progress`,
  `/pregnancies/current/dating`) are idempotent → safe to retry.
- `POST /v1/pregnancies`, `POST /v1/reminders`, `POST /v1/me/consents`,
  `POST /v1/anonymous-sessions` are **not idempotent and have no idempotency-key support**. The
  client must never auto-retry them; duplicate taps are blocked in-flight and a timeout is
  resolved by re-reading (`GET /v1/pregnancies/current`), not by resending.
- `POST /v1/me/export` and `POST /v1/me/deletion` are never retried automatically.

## 8. Gaps — requested features with no backend support

| Feature requested | Backend today | Proposed handling |
|---|---|---|
| **Appointments** (list, create, reschedule, complete, delete, notes) | No route, no `Appointment` table | Needs a decision: local-only (device storage, labelled unsynced) **or** a new backend module (your approval required) **or** deferred |
| **Nutrition / meal log / water intake** | Nothing. Profile holds `dietPattern`, `foodAllergies` only | Same decision. Note: PRD §15 deliberately defers food logging; no calorie or macro targets will be prescribed either way |
| **Exercise logging** | Nothing. `restrictExercise` flag only | Same decision; educational content + safety guidance can ship without any endpoint |
| **Mood / sleep / reflection journal** | `mood_low`, `mood_irritable` codes + free note in daily logs | Use daily logs where it fits; anything richer needs a decision |
| **Hospital bag / birth preparation checklists** | Nothing (readiness tasks are preconception) | Local-only checklist, or new content via the existing admin task workflow |
| **Symptom severity, duration, pregnancy symptoms** | Fixed 14-code list, no severity | Backend change required for severity; app will not fake it |
| **Article categories, search, related articles** | No fields | Client-side filtering of fetched pages only, scoped honestly |
| **Push notifications** | `/v1/reminders` stores preferences; no device-token route, no scheduler, no push provider | **Local notifications only** (on-device scheduling from reminder rows). Server-driven push is a documented missing dependency |
| **Premium purchase** | `GET /v1/me/entitlement` reads verified subscriptions; **no store-receipt verification or webhook** | Locked states render; no purchase flow. Entitlement is always `none` |
| **Password reset / email verification** | Disabled (404) | No "Forgot password?" in the UI |
| **Multi-locale** | `en` only | No language switcher |
| **Localised emergency numbers** | `profile.countryCode` exists; no verified number data | Only verified numbers shown, else "contact your maternity unit" |

## 9. Endpoints the mobile app will not call

All 17 `/v1/admin/*` routes (staff + 2FA; the admin web app owns these), the cycle endpoints
`/v1/cycles*` (preconception period tracking — out of scope for a pregnancy app, and available if
you want it), and the 2FA Better Auth routes (staff-only today).

## 11. Open decisions

1. **Appointments, nutrition, hydration, exercise, mood, checklists:** local-only, new backend
   modules (needs your approval), or deferred?
2. **Content:** ship honest empty states, or author week guides / articles from official sources
   first? Content cannot be labelled clinically reviewed without a real reviewer.
3. **Symptom severity:** accept the existing fixed vocabulary without severity, or extend the
   backend?

Resolved on 2026-10-19: (1) local-only with a visible "saved on this device" marker, no backend
change; (2) honest empty states, no invented content; (3) keep the existing fixed symptom
vocabulary without severity. `docs/KNOWN_LIMITATIONS.md` records each one.
